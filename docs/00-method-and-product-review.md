# 方法与产品审计

## 1. 审计范围

- 产品：YeahPromos 商家侧站内后台
- 目标：在视觉探索前，确定全量站内功能框架
- 证据：`pb_manual_images` 中 40 张 PartnerBoost 商家手册图片
- 审计模式：产品流程、信息架构与可访问性风险的联合审计
- 限制：素材不是连续录屏，也不含真实接口、权限配置、响应式行为或错误处理；因此不能据此声称完整可用性或 WCAG 合规

## 2. 对方法的判断

### 结论

“先冻结功能与分支，再生成不同视觉风格”是合理且风险更低的方法，值得继续。关键是把本阶段定义成 **产品契约阶段**，而不是“先画一个无风格的页面”。

### 为什么有效

- 可把“功能完整性”与“视觉偏好”分开评审。
- 多个风格方案能基于同一套任务和数据比较，不会一个方案功能多、另一个方案功能少。
- 研发可以提前识别实体、状态、权限和集成边界。
- 后续改风格时不必反复重做页面关系与数据结构。

### 需要补强的地方

1. **不要只确认栏目名称。** 需要同时确认页面目标、字段、动作、状态、权限和异常。
2. **不要让截图成为唯一真相。** 截图能证明已有能力，不能证明未来业务优先级；导航中仅被提及的模块必须单独补需求。
3. **不要为每种风格复制一套产品。** 后续视觉方向应共享一个框架版本和一套验收任务。
4. **先定义比较标准。** 高保真方案应统一比较任务完成效率、信息清晰度、品牌感、可访问性和响应式表现。
5. **把业务决定显式化。** 例如达人与媒体是否分开、CPI 是否保留、商品规则是否只允许白名单，不能留到高保真阶段才决定。

## 3. 现有体验的主要优点

### 功能覆盖已经很广

素材证明现有体系已经覆盖了伙伴发现、邀请、审核、关系管理、商品、优惠券、佣金、报表、交易、支付和团队权限。升级不应以删功能为目标，而应降低理解和操作成本。

### 对达人与媒体保留了不同画像

达人画像强调社交平台、粉丝、内容和互动；媒体画像强调推广方式、站点渠道、受众地域、排名和访问。这两个对象不应被强行压成完全相同的数据卡片。

### 已存在跨品牌和团队权限概念

品牌切换、多账号、品牌级权限和模块树为商家团队协作提供了基础。这是全量升级时必须保留的企业级能力。

### 数据可下钻和导出

绩效、品牌、订单和 Amazon BRB 报表具有筛选、维度切换、下钻与 CSV 导出，适合继续演化为统一分析工作区。

## 4. 结构性问题

### 4.1 导航按系统能力分类，不按商家任务分类

`Partners / Campaigns / Creatives / Tools / Reports` 更像内部模块边界。商家实际任务是“找到伙伴 → 建立合作 → 准备推广内容与规则 → 追踪订单 → 结算”。相邻任务被分散在不同菜单，增加了寻找成本。

**建议：** 顶层改成任务域，旧模块作为二级页面保留。详见 [信息架构](01-information-architecture.md)。

### 4.2 同一审核队列存在多个入口

待审核伙伴可以从 `Pending Partners`、`New Partners` 和状态统计卡进入。多个入口不是问题，但它们必须落到同一队列、使用同一状态和同一筛选上下文，否则商家会误以为是三种不同待办。

**建议：** 总览显示统一待办数量，点击进入一个“申请审核”页；入口只负责预设筛选条件。

### 4.3 伙伴状态口径重叠

顶部出现 `In Relationship / Followed / Invited / Pending / Declined`，页内又有 `Joined / New Partners / Followed / Blocked`。`In Relationship` 与 `Joined`、`Pending` 与 `New Partners` 的关系不够直观。

**建议：** 建立单一关系状态机，并把“关注”作为商家个人/团队标记，不与合作关系状态混用。

### 4.4 达人与媒体发现操作依赖图标猜测

卡片同时出现邀请、消息、关注、奖励、屏蔽及更多操作，大量无文字图标提高学习成本，也容易造成误操作。

**建议：** 每张卡保留一个主动作和一个明确的次级菜单；危险动作进入二次确认；所有图标具备文本标签、提示和键盘焦点。

### 4.5 配置分散在多个顶层模块

商品与优惠券在 `Creatives`，佣金规则、归因、PPC 和链接参数在 `Tools`，品牌和支付方法在 `Settings`。这些实际上共同决定一个推广计划能否运行。

**建议：** 将“商品与推广资产”和“佣金与规则”设为相邻任务域，并在活动配置中显示依赖完整度。

### 4.6 报表页面重复，维度控制负担高

绩效与品牌绩效使用相似图表和表格，但以不同页面重复呈现；筛选器、分组维度和指标同时平铺，首次使用者难以判断先做什么。

**建议：** 统一为分析工作区：先选范围，再选指标，再选分组；品牌只是范围或维度之一。保留快捷视图和保存报告，不要求用户每次从零组合。

### 4.7 关键操作缺少可见的系统反馈

素材展示了大量空状态和表单，但没有充分证明加载、发送中、导入失败、部分成功、同步冲突、导出排队、权限不足等状态。

**建议：** 这些状态在功能框架阶段就要列入，不应留给视觉设计临时补齐。

### 4.8 账号权限页存在安全与理解风险

账号列表包含密码掩码列，但用户真正需要的是登录状态、角色、品牌范围和最近活动，而不是“看见有一个密码”。权限又通过大型模块树移动到允许区，容易漏配或过度授权。

**建议：** 列表移除密码列，使用“邀请/重置密码”；权限采用角色模板 + 品牌范围 + 例外权限，并提供生效结果预览与审计记录。

## 5. 可访问性与响应式风险

从静态素材可见的风险包括：

- 小尺寸纯图标按钮的含义和点击区域不明确。
- 灰色辅助文字、空状态与淡色状态卡可能存在对比度不足。
- 筛选器和表格列数量过多，缩放或窄屏下容易水平溢出。
- 颜色承担了大量状态表达，需要同时提供文字和图形标识。
- 侧滑面板和弹窗较多，需要明确焦点锁定、关闭方式和返回焦点。
- 富文本编辑器、日期范围、级联条件和权限树需要完整键盘操作与可读标签。

以上只能作为设计风险；最终必须通过实现后的键盘、读屏、缩放、对比度和响应式测试验证。

## 6. 建议的阶段门

### Gate A：功能框架确认（当前）

- 顶层信息架构确认
- P0 页面、字段、动作和状态确认
- 导航中证据不足模块的去留确认
- 角色、品牌范围和关键业务规则确认

### Gate B：低成本流程原型

- 只验证关键任务顺序和页面跳转
- 不把视觉风格作为评审重点
- 对每条 P0 流程验证成功、空、错误和权限分支

### Gate C：三种高保真方向

- 使用相同页面、数据和任务
- 每种方向至少覆盖：总览、伙伴发现、伙伴详情/邀请、分析、复杂表单
- 统一桌面与移动视口，统一可访问性底线

### Gate D：方向选择与生产化

- 选择一个方向后再完善设计系统、响应式、动效和工程实现
- 未选择的方向保留为探索证据，不继续分叉产品功能
